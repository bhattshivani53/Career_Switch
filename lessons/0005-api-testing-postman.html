API Testing with Postman

The skill that separates good Junior QAs — testing what users never see, but always rely on.

⏱ 45–60 minutes 🛠 Postman + Juice Shop API 🔌 You will send real API requests today

1. What is an API — and Why Do We Test It?

Every time you use an app, two things are happening at once:

  • The UI (User Interface) — what you see and click: buttons, forms, pages
  • The API (Application Programming Interface) — the invisible layer underneath that fetches, saves, and processes data

When you search for "apple" on the Juice Shop, your browser sends a request to an API endpoint, the API fetches matching products from a database, and the UI displays them. The UI is just a wrapper around the API.

Healthcare Parallel

Think of a hospital blood test. The UI is the form you fill in at the reception desk. The API is the lab system underneath — the one that actually processes the sample, stores results in the database, and sends them to the doctor's system.

You could test the reception form perfectly and miss a critical bug in the lab system. API testing goes directly to the lab — no form needed.

Why QAs test APIs, not just UIs

  • Faster — no browser to load, no clicks required. API tests run in milliseconds.
  • More thorough — you can send data the UI would never allow (e.g., negative quantities, missing fields)
  • Catches more bugs — the UI might mask an API error with a friendly message; API testing sees the raw truth
  • Earlier — the API exists before the UI is built. You can start testing in week one of a sprint

2. REST APIs — The Standard You'll Always Work With

A REST API works like a conversation between two systems. Your tool (Postman) sends a request, and the server sends back a response.

Every request has four parts:

PartWhat it isExample
MethodWhat you want to DOGET fetch data
URL (Endpoint)WHERE on the serverhttp://192.168.0.202:9058/api/Products
HeadersMeta-information (auth token, content type)Content-Type: application/json
BodyData you're sending (POST/PUT only){"email": "test@test.com"}

3. HTTP Methods — The Four You Must Know

MethodWhat it doesJuice Shop exampleHealthcare analogy
GET Retrieve data. Never changes anything. Fetch list of products Reading a patient's medical record
POST Create new data Register a new user account Admitting a new patient into the system
PUT Replace existing data completely Update a user's full profile Replacing an entire patient record
DELETE Remove data Delete a basket item Removing a patient from a ward list
The Golden Rule of GET

A GET request must never change data. If a GET request creates, updates, or deletes anything — that is a bug. Always test this.

4. HTTP Status Codes — Know These Cold

Every API response includes a 3-digit status code. This is how the server tells you whether your request succeeded or failed — and why.

200
OK
Request succeeded. Data returned.
201
Created
New resource created successfully (POST).
204
No Content
Success, but no data to return (often DELETE).
400
Bad Request
Request was malformed — missing field, wrong format.
401
Unauthorized
Not logged in — authentication required.
403
Forbidden
Logged in, but not allowed to do this.
404
Not Found
Resource doesn't exist at this URL.
500
Server Error
The server crashed. Always a bug worth raising.
Interview: 401 vs 403 — Everyone Gets This Wrong

401 Unauthorized = "I don't know who you are — please log in first."
403 Forbidden = "I know exactly who you are — and you're not allowed to do this."

Healthcare: 401 = a stranger trying to enter a ward without a badge. 403 = a nurse trying to access the consultant's private notes — authenticated, but not authorised.

5. Getting Started with Postman

Postman is a free tool for sending API requests. Download it at postman.com/downloads if you haven't already. The desktop app is best.

Open Postman → New Request

Click the + tab to create a new request. You'll see a URL bar and a method dropdown (GET, POST, etc.).

Set the method and URL

Select GET from the dropdown. Type the URL: http://192.168.0.202:9058/api/Products

Click Send

Postman sends the request. In the bottom panel you'll see the Status code, Time, and the Response body — a JSON list of all Juice Shop products.

Read the response

Look at: the status code (should be 200), the response time (milliseconds), and the JSON body. Each product has an id, name, description, price, and image.

Create a Collection

Click Save → New Collection → name it "Juice Shop API Tests". Save each request here. A collection is like a test suite — but for API tests.

6. The Juice Shop API — Your Test Targets

Here are the key endpoints you'll work with. All requests go to base URL http://192.168.0.202:9058.

MethodEndpointWhat it doesExpected status
GET/api/ProductsGet all products200
GET/api/Products/1Get product with ID 1200
GET/api/Products/9999Get a product that doesn't exist200 or 404*
POST/rest/user/loginLog in with email + password200
POST/rest/user/loginLog in with wrong password401
POST/api/UsersRegister a new user201
GET/rest/user/whoamiGet currently logged-in user200

* Sending actual results back matters — what the Juice Shop returns for a non-existent product is itself a QA finding.

Example 1 — GET all products

GET http://192.168.0.202:9058/api/Products
Response — 200 OK
{ "status": "success", "data": [ { "id": 1, "name": "Apple Juice (1000ml)", "description": "The all-time classic.", "price": 1.99, "image": "apple_juice.jpg" }, ... ] }

Example 2 — POST login (valid credentials)

POST http://192.168.0.202:9058/rest/user/login
Headers
Content-Type: application/json
Body (raw JSON)
{ "email": "admin@juice-sh.op", "password": "admin123" }
Response — 200 OK
{ "authentication": { "token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...", "bid": 1, "umail": "admin@juice-sh.op" } }

Example 3 — POST login (wrong password)

POST http://192.168.0.202:9058/rest/user/login
Body (raw JSON)
{ "email": "admin@juice-sh.op", "password": "wrongpassword" }
Response — 401 Unauthorized
{ "error": "Invalid email or password." }

7. What to Check in an API Test

When you send a request, check all four of these — not just the status code:

CheckWhat to look forExample
Status codeIs it the right code for this scenario?GET a product → expect 200, not 500
Response bodyIs the data correct and complete?Product name, price, description all present?
Response timeIs it fast enough? (under 2000ms is typical)If GET /Products takes 8 seconds → performance bug
HeadersSecurity headers present? Content-type correct?Response should say Content-Type: application/json

Exercise — Your First API Test Session

TASK 1 — WARM UP (GET)

In Postman, send these two requests and note the status code and what comes back:

  • GET http://192.168.0.202:9058/api/Products — how many products? What status?
  • GET http://192.168.0.202:9058/api/Products/1 — what product is ID 1? What's its price?

TASK 2 — NEGATIVE TEST (GET)

  • GET http://192.168.0.202:9058/api/Products/9999 — what status code do you get? What does the body say? Is this what you'd expect?

TASK 3 — POST (LOGIN)

Select POST. URL: http://192.168.0.202:9058/rest/user/login

Go to Body → raw → JSON and paste:

{
  "email": "admin@juice-sh.op",
  "password": "admin123"
}

Click Send. What status do you get? Do you see a token in the response?

TASK 4 — NEGATIVE POST (WRONG PASSWORD)

Same endpoint, change the password to "wrongpassword". What status code comes back? What does the error say?

TASK 5 — FIND A BUG

Try this: GET http://192.168.0.202:9058/api/Users

You are not logged in. What status code do you expect? What status do you actually get? If actual ≠ expected — that's a bug. Note it down.

TASK 6 — REPORT BACK

Tell me:

  • What status came back for /api/Products/9999?
  • Did you get a token from the login POST?
  • What happened with GET /api/Users?

Quick Check — 5 Questions

1. You send a GET request to /api/Products/99 and get a 404. What does this mean?

2. You successfully register a new user via POST. Which status code should the API return?

3. What is the difference between a 401 and a 403 response?

4. Why is API testing valuable even when UI testing is also done?

5. A GET request to /api/Orders deletes all orders in the database. Is this a bug?
