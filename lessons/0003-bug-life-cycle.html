The Bug Life Cycle — and Your First Real Bug Report

How a bug is born, tracked, fixed, verified, and closed — and how to write one that developers actually act on.

⏱ 35–45 minutes 🛠 Tools: Juice Shop + YouTrack Issues 🐛 You will find and raise a real bug today

1. What is a Bug?

A bug (defect) is when software behaves differently from how it is supposed to behave — based on requirements, design, or common sense.

Three types of difference matter:

  • Functional defect — the feature does the wrong thing (wrong calculation, wrong navigation, data not saved)
  • UI defect — the interface looks wrong (broken layout, wrong text, element in wrong position)
  • Performance defect — the feature does the right thing but too slowly
Healthcare Parallel

A bug is like an adverse event report in healthcare. Something happened that shouldn't have (or didn't happen that should have). You document exactly what occurred, the conditions under which it happened, and the impact — so it can be investigated, fixed, and verified.

The discipline is the same: accurate observation + clear documentation + escalation to the right person.

2. The Bug Life Cycle

Every bug goes through a set of states from discovery to closure. Understanding this is essential — you will be managing bugs in YouTrack from day one.

Assigned

In Progress

But the cycle isn't always linear. Here are the important branch states:

StateWho sets itWhat it means

The QA's Core Responsibility in the Bug Cycle

You are responsible for New → Retest → Closed/Reopened. You raise the bug, you re-test after the fix, and you make the final call on whether it's fixed. The developer does not close their own bugs — QA does.

3. Severity vs Priority — The Difference That Trips Everyone Up

This comes up in almost every QA interview. They are two completely different dimensions.

Severity

How bad is the technical impact?
Set by: QA

  • Critical — System crash, data loss, security breach, complete feature broken
  • Major — Core feature partially broken, no workaround
  • Minor — Feature partially broken but workaround exists
  • Trivial — Cosmetic issue — typo, colour off, icon wrong

Priority

How urgently must it be fixed?
Set by: Product Manager

  • High — Must be fixed before release / immediately
  • Medium — Fix in current or next sprint
  • Low — Fix when time allows

The trick: severity and priority can go in opposite directions.

ScenarioSeverityPriorityWhy?
The CEO's name is spelled wrong on the homepage Trivial High Low technical impact, but politically urgent to fix immediately
A crash occurs only when a user selects a currency no one uses Critical Low Severe when it happens, but almost no users trigger it
Login page is completely broken Critical High Both — blocks all users, must be fixed immediately
A minor UI misalignment on the about page Trivial Low Both — barely anyone sees it, low urgency
Interview Answer

"Severity is a technical measure of how bad the bug's impact is — set by QA. Priority is a business decision about how urgently it needs to be fixed — set by the product manager. They're independent: a trivial typo on the CEO's bio page might be Priority High even though it's Severity Trivial, because the business needs it fixed before the press launch."

4. Anatomy of a Professional Bug Report

A bug report is only useful if a developer can reproduce it. If they can't reproduce it, they can't fix it. Your job is to give them everything they need.

Here is a real example — a bug you can find in the Juice Shop right now:

BUG_LOGIN_001 Login — Security Severity: Critical
Title
Application allows login with SQL injection in the email field, bypassing authentication entirely
Environment
OWASP Juice Shop · http://192.168.0.202:9058 · Chrome 126 · macOS
Steps to Reproduce
  1. Navigate to http://192.168.0.202:9058/#/login
  2. Enter ' OR 1=1-- in the Email field
  3. Enter anything in the Password field (e.g. abc)
  4. Click the "Log In" button
Expected Result
Login fails. An error message is displayed: "Invalid email or password." No account is accessed.
Actual Result
User is logged in as admin@juice-sh.op without providing a valid password. Full admin account access is granted.
Severity
Critical — authentication is completely bypassed; any attacker can access any account
Priority
High — must be fixed immediately before any production deployment
Attachments
Screenshot showing admin@juice-sh.op logged in after SQL injection input
Important Context

The Juice Shop is deliberately built with vulnerabilities like this — it's a training app, not a real shop. In your future job, finding a SQL injection vulnerability in a real app would be an immediate Critical/High bug that stops the release. In healthcare IT especially — SQL injection in a patient record system could expose thousands of records.

The Seven Fields You Must Always Include

FieldWhy it's essential
TitleMust describe the bug in one sentence — what fails, in what context
EnvironmentBrowser, OS, app version — a bug on Chrome may not appear on Firefox
Steps to ReproduceNumbered, exact steps — if the developer can't follow them, they can't fix it
Expected ResultWhat SHOULD have happened, based on requirements
Actual ResultWhat DID happen — be precise, not "it broke"
SeverityYour technical assessment of the impact
AttachmentsScreenshot or screen recording — a picture saves 10 back-and-forth messages

5. What Makes a Good vs Bad Bug Title

Bad titleWhy it's badGood title
"Login doesn't work" No context — which login? what happens? when? "Login fails with valid credentials when email contains uppercase letters"
"Registration bug" Tells the developer nothing "Registration form accepts duplicate email without showing an error"
"Error on checkout" Which error? When exactly? "500 Server Error displayed when user proceeds to checkout with an empty basket"

A good bug title answers three questions in one sentence: What failed? Where (which feature)? Under what condition?

Exercise — Find and Raise Your First Real Bug

The Juice Shop contains many intentional bugs. Your job is to find one and raise a professional bug report in YouTrack Issues (not Test Manager — this goes in the main Issues list, on the Juice Shop Testing board).

STEP 1 — FIND THE BUG

Try this on the Juice Shop login page: http://192.168.0.202:9058/#/login

  • Enter exactly this in the Email field: ' OR 1=1--
  • Enter anything in the Password field
  • Click Log In
  • Note what happens

Then also try this on the Registration page: register with the email test@test.com — then try registering again with the exact same email. Does the app handle it clearly?

STEP 2 — RAISE IT IN YOUTRACK

Go to YouTrack → Issues → New Issue (not Test Manager). Fill in all seven fields from Section 4:

  • Title: one sentence — what fails, where, under what condition
  • Type: Bug
  • Project: Juice Shop Testing
  • Steps to Reproduce: numbered, exact
  • Expected Result: what should happen
  • Actual Result: what actually happened
  • Severity: Critical / Major / Minor / Trivial
  • Attach a screenshot

STEP 3 — MOVE IT ON THE AGILE BOARD

Go to Agile Boards → Juice Shop Testing. Find your new bug. Drag it from "To Do" to "In Progress" (pretend you're investigating it). This is how you interact with the board as a QA.

STEP 4 — SHARE WITH ME

Send a screenshot of your bug in YouTrack Issues. I'll review the title, steps, severity, and whether the expected/actual results are clear. That's your feedback loop before Lesson 04.
