Lesson 06

Test Design Techniques

Stop testing randomly. Learn how to find more bugs with fewer test cases — the way senior QAs actually do it.

Equivalence Partitioning Boundary Value Analysis Decision Tables ISTQB Syllabus
🎯

Why Do We Need Techniques?

Imagine testing a password field. It can be 0 to 100 characters. If you test every single length — 0 chars, 1 char, 2 chars... 100 chars — that's 101 test cases for one field. Now add the email field, the username field, security questions...

You'd never finish. And most of those tests would tell you nothing new.

The insight

Test design techniques let you achieve maximum coverage with minimum test cases. They're based on the proven idea that inputs in the same group behave the same way — so you only need one test from each group.

Healthcare analogy

When a patient arrives in A&E, doctors don't run every test in the hospital. They use clinical decision rules — systematic protocols that tell them exactly which tests to run based on symptoms and risk factors. Same principle: structured thinking to cover all important cases efficiently.

Equivalence Partitioning (EP)

The Core Idea

Divide the input space into partitions — groups of values that should all produce the same result. If one value in a partition causes a bug, all values in that partition will cause the same bug.

So instead of testing 100 values, you test one representative value per partition.

Juice Shop Example — Registration Password Field

The Juice Shop registration form requires a password of at least 5 characters. Let's apply EP:

Invalid Partition
0 – 4 chars
e.g. "abc" (3 chars)
Should REJECT
Valid Partition
5+ chars
e.g. "password1" (9 chars)
Should ACCEPT
Invalid Partition
Passwords don't match
Pass: "abc123" Repeat: "abc124"
Should REJECT
The saving

Password could be any of millions of values. EP reduces this to 3 test cases: one from each partition. You don't need to test "abc", "abcd", "a", "12", "!!" — they're all in the same invalid partition and behave the same way.

Boundary Value Analysis (BVA)

The Core Idea

EP tells you which groups to test. BVA tells you which values within those groups to choose. The answer: always test at the boundaries between partitions.

Why? Because developers often write conditions like if length > 5 when they meant if length >= 5. Off-by-one errors are extremely common. Boundaries catch them.

The boundary rule

For every boundary: test (min−1), min, min+1 and max−1, max, max+1. The boundary itself is the most critical value — if you can only test one value, test exactly at the boundary.

Decision Tables

The Core Idea

Some features don't depend on a single input — they depend on combinations of conditions. A decision table maps every combination of conditions to the expected outcome.

Use this when you see words like "AND", "OR", "IF", "UNLESS" in requirements.

Juice Shop Example — Login Form

The login page has two conditions: is the email registered? Is the password correct? These combine to produce four possible outcomes:

Condition / Outcome TC-01 TC-02 TC-03 TC-04
Email is registered Y Y N N
Password is correct Y N Y N
Expected outcome Login success Error: Invalid email or password Error: Invalid email or password Error: Invalid email or password
Key insight

Notice TC-02, TC-03, and TC-04 all produce the same error message. The app deliberately doesn't tell you which thing was wrong — that's a security feature (it prevents attackers from knowing which emails are registered). Your decision table revealed this by forcing you to think through all combinations.

Quick Check

1. A registration form accepts ages 18–65. Using EP, which set of test values gives the best coverage?
✅ Correct! One value from each partition: below 18 (invalid), 18–65 (valid), above 65 (invalid). Three test cases instead of 100.
❌ Not quite. EP means one value per partition. The three partitions are: <18 (invalid), 18–65 (valid), >65 (invalid). One from each is enough.
2. A search field accepts 1–100 characters. Which values should you test using BVA?
✅ Correct! BVA tests: just below min (0), at min (1), just above min (2), just below max (99), at max (100), just above max (101). Boundaries on both sides.
❌ BVA tests at and around the boundaries: 0 (below min), 1 (at min), 2 (just above min), 99 (just below max), 100 (at max), 101 (above max). Not just the endpoints.
3. When should you use a Decision Table?
✅ Correct! Decision tables are for complex logic with multiple conditions. Look for "AND", "OR", "IF" in requirements — that signals you need a decision table.
❌ Decision tables are specifically for situations where multiple conditions combine to affect the result. If you see conditions like "IF email valid AND password correct THEN..." — that needs a decision table.
4. You find that a password field with minimum 8 characters accepts "abcde" (5 chars). What type of bug is this?
✅ Correct! 5 chars is in the invalid partition (below minimum 8). BVA caught it — "abcde" should be rejected but wasn't. This is a validation bug, specifically at the boundary.
❌ If minimum is 8 and "abcde" (5 chars) is accepted, that's a bug. The field is NOT enforcing its minimum correctly. 5 chars should be rejected — this is a boundary validation failure.
5. In your decision table for Juice Shop login, how many test cases do you need if there are 2 conditions (email registered Y/N, password correct Y/N)?
✅ Correct! 2 conditions × 2 values each (Y/N) = 2² = 4 combinations. TC-01: Y+Y, TC-02: Y+N, TC-03: N+Y, TC-04: N+N. Always 2^n combinations for n binary conditions.
❌ With 2 binary conditions: 2² = 4 combinations. Y+Y, Y+N, N+Y, N+N. For 3 conditions it would be 2³ = 8. The formula is 2^n for n binary conditions.

Interview Questions — Answered

"What is equivalence partitioning? Give me an example."
"Equivalence partitioning is a test design technique where you divide the input space into groups — called partitions — that should all behave the same way. If one value in a partition causes a bug, they all will, so you only need to test one value per partition. For example, when testing a password field with a 5-character minimum, I'd identify three partitions: passwords under 5 chars (invalid), passwords of 5 or more chars (valid), and passwords that don't match the repeat field (invalid). I'd test one value from each — so three test cases instead of thousands."
"What is boundary value analysis and why is it useful?"
"Boundary value analysis extends equivalence partitioning by specifically targeting the edges between partitions. Developers often make off-by-one errors — writing > instead of >= — and these bugs appear right at boundaries. So for a field that accepts 5 to 100 characters, I'd test 4 (just below minimum), 5 (at minimum), 6 (just above minimum), then 99, 100, and 101 at the maximum. These six values are far more likely to expose bugs than any random value in the middle."
"How would you test a login form?"
"I'd use a decision table. A login form depends on at least two conditions: whether the email is registered and whether the password is correct. These combine to give four scenarios. I'd write a test case for each: valid email + correct password (expect success), valid email + wrong password (expect error), unregistered email + any password (expect error), and empty fields (expect validation message). Then I'd apply BVA to the password field specifically — testing the minimum length boundary — and EP to the email field to cover valid, invalid format, and empty partitions."
The phrase that lands well in interviews

"I use test design techniques to achieve maximum coverage with minimum test cases. EP tells me which groups to test, BVA tells me which values to pick within those groups, and decision tables handle complex conditions. Used together, they make testing systematic rather than random."
