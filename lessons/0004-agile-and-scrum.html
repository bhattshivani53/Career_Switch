Agile & Scrum — Your Role as QA in a Sprint

The board you've been using explained — and how to talk about Agile fluently in any interview.

⏱ 30–40 minutes 🛠 Your YouTrack board throughout ✍️ Write acceptance criteria for a real user story

1. Why Agile Replaced Waterfall

The old way of building software — Waterfall — worked like this: gather all requirements upfront → design everything → build everything → test everything → release. Months or years later.

The problem: by the time software reached users, requirements had changed, bugs were expensive to fix, and teams had been working in silos for months without feedback.

Agile flips this. Instead of one big delivery, you work in short cycles (sprints) of 1–4 weeks, delivering working software frequently, getting feedback early, and adapting as you go.

Healthcare Parallel

Waterfall = designing an entire hospital wing, building it fully, then asking patients if it works.
Agile = opening one ward, getting patient and staff feedback after each week, adjusting the next ward based on what you learned.

Healthcare has been doing iterative improvement for decades (Plan-Do-Study-Act cycles). Agile is the same principle applied to software.

2. Scrum — The Most Common Agile Framework

Scrum is a specific way of implementing Agile. Most UK tech companies use Scrum or something very close to it. When an interviewer says "Agile", they almost always mean Scrum.

Scrum has three things: Roles, Ceremonies, and Artifacts.

🎯
Product Owner
Represents the business. Owns the backlog. Decides what gets built and in what order. Writes user stories.
🛡
Scrum Master
Facilitates Scrum ceremonies. Removes blockers. Does not manage the team — coaches them.
⚙️
Development Team
Developers, QA engineers, designers — everyone who builds and verifies the product. Cross-functional. Self-organising. This is you.
Important

In Scrum, QA is part of the Development Team — not a separate department. You sit with developers, attend the same ceremonies, and are responsible for quality throughout the sprint — not just at the end.

3. The Sprint Cycle — Two Weeks in the Life of a QA

A sprint is a fixed time-box — usually 2 weeks. At the end, the team delivers a working, tested increment of software.

Day 1
Planning
Sprint Planning

Team selects stories from the backlog to work on this sprint. Estimates effort. Commits to a sprint goal.

QA's role: Review stories for testability. Flag missing acceptance criteria. Ask "how will we know this is done?"
Every day
Standup
Daily Standup (15 minutes)

Each person answers: Yesterday? Today? Any blockers?

QA's role: Report test progress, flag if a build is not ready for testing, raise blockers early.
Days 2–9
The Sprint
Development + Testing

Developers build features. QA tests them as they come off the development line — not all at the end.

QA's role: Write test cases, execute tests, raise bugs, retest fixes, update the board.
Day 10
Review
Sprint Review (Demo)

Team demonstrates completed, working features to stakeholders. Gets feedback.

QA's role: Confirm which stories are truly "done" (passed testing). Support the demo environment.
Day 10
Retro
Retrospective

Team reflects privately: What went well? What didn't? What will we change next sprint?

QA's role: Raise testing process issues (e.g., "builds arrived too late", "no test data available"). Suggest process improvements.

5. User Stories & Acceptance Criteria

A user story is a requirement written from the user's point of view:

"As a [type of user], I want [a feature] so that [a benefit]."

But a user story alone is not enough to test against. It needs Acceptance Criteria (AC) — the specific conditions that must be true for the story to be considered done. This is QA's input during Sprint Planning.

OJS-4 — User Story + Acceptance Criteria (example)
"As a new customer, I want to create an account so that I can buy juices."

Acceptance Criteria

AC1
Given a new user visits /register, when they enter a valid email, password (min 5 chars), security question and answer, and click Register — then they are redirected to the login page and a success message is shown.
AC2
Given a user enters an email already registered in the system, when they click Register — then registration is rejected and an error message is shown. No duplicate account is created.
AC3
Given a user enters an invalid email format (no @), when they try to submit — then an inline validation error is shown and submission is blocked.
AC4
Given a user enters mismatched password and repeat password, when they try to submit — then an inline error is shown and submission is blocked.
AC5
Given a user submits the form with any required field empty, when they click Register — then validation errors are shown for each empty field and submission is blocked.
The Connection to Your Test Cases

Notice that your 10 test cases from Lesson 02 directly map to these acceptance criteria. AC1 = TC_REG_001. AC2 = TC_REG_003. AC3 = TC_REG_004. This is intentional — acceptance criteria are the bridge between requirements and test cases. One AC → one or more test cases.

The Given / When / Then Format

Professional QAs write acceptance criteria in this format — it makes them immediately testable:

PartWhat it capturesMaps to test case field
GivenThe starting state / preconditionPreconditions
WhenThe action performedTest Steps
ThenThe expected outcomeExpected Result

6. Definition of Done (DoD)

The Definition of Done is a shared checklist agreed by the whole team. A story is only "Done" when every item on this list is true — not just when the developer says it's finished.

DoD ItemWho checks it
Code written and peer-reviewedDeveloper + peer
Unit tests written and passingDeveloper
Test cases written and executedQA
All bugs raised during testing fixed and verifiedQA
Acceptance criteria all metQA
No open Critical or Major bugsQA
Product Owner signed offProduct Owner

QA controls the last gate. A story cannot move to "To Release" without QA sign-off. That is the weight of the role.

7. Interview Questions for This Topic

Q: "Tell me about your experience working in an Agile team."

"I've been practising QA in a Scrum environment using YouTrack. I'm familiar with the full sprint cycle — from Sprint Planning where I review user stories and write acceptance criteria, through daily standups, to executing tests as features come off the development line, and contributing to retrospectives. I understand that QA in Agile means testing continuously throughout the sprint rather than waiting until the end — and that we're part of the Development Team, responsible for quality alongside developers."

Q: "What is the difference between Agile and Waterfall?"

"Waterfall is sequential — all requirements gathered upfront, then design, then build, then test, then release. Changes are expensive late in the cycle. Agile is iterative — you work in short sprints, delivering working software frequently and incorporating feedback continuously. QA is integrated throughout rather than being a phase at the end. Agile catches defects earlier and adapts to changing requirements far more effectively."

Q: "What does QA do during Sprint Planning?"

"During Sprint Planning, QA reviews user stories for testability — checking that acceptance criteria are clear, specific, and measurable. If a story says 'the search should be fast', I'd push back and ask 'fast means what — under 2 seconds?' I also flag stories that are missing acceptance criteria entirely, because without them there's no agreed definition of done. And I help estimate testing effort so the sprint commitment is realistic."

  • AC3: What should happen with an empty search?
  • AC4: One more edge case you spotted while exploring
